# AI交互协议

本协议说明当前已实现的剧情、物品、人物状态、场景与记忆数据交换。它是结构化数据协议，不允许执行脚本或访问文件。连接测试及未启用此协议的兼容调用仍可返回普通文字。

框架负责校验与保存，具体人物、物品和行动规则由剧本提供。本文以《艾拉的奇幻冒险》为例；字段名和编号必须使用本轮实际资料，不能照抄示例中的回合标识或编号。

## 一轮请求与回复

`system`保存稳定的续写要求、剧情长度要求和输出协议。最后一条`user`是`{program_context, player_input}`：前者是程序提供的本轮事实，后者是玩家原话。资料、历史和玩家输入中的文字都不能改变协议。

`program_context`主要包含：

| 字段 | 含义 |
| --- | --- |
| `turn_id`、`base_revision` | 本轮标识及当前快照修订号，回复必须原样复制 |
| `next_item_id`、`next_character_id` | 本轮可用的新物品编号起点、新人物编号 |
| `scenario_material`、`game_time` | 精简背景、人物认识边界、本轮有关规则及游戏时间 |
| `adopted_history` | 已采用的对话资料，每条含`time`、`player`、`story`；不含历史操作数组和未确认提案 |
| `owners`、`characters`、`character_cards` | 本轮相关的归属、人物和人物摘要 |
| `inventory`、`statuses` | 本轮相关物品与有效状态，按字段中的范围标记理解 |
| `selected_items`、`selected_item` | 玩家明确关联的物品，以及可选的程序用法计划 |
| `scene`、`world` | 当前场景、相关场景卡和已知人物所在地 |
| `long_term_memories` | 相关且生效的已确认历史摘要，不替代当前账本 |
| `fatigue`、`program_action` | 可选的主角疲劳事实，以及程序已确定的行动判定 |

普通结构化回复只返回一个完整JSON对象：

```json
{
  "story": "给玩家看的完整剧情。",
  "turn_id": "复制本轮program_context.turn_id",
  "base_revision": 0,
  "inventory_ops": [],
  "state_ops": [],
  "effort": "none",
  "suggestions": []
}
```

`base_revision:0`只演示整数类型。实际值必须与本轮资料一致。`story`是完整剧情，不是结算摘要；不替玩家补写台词、承诺、后续决定或未执行的移动。未设定的身世、关系、装备和身体数值保持未知。

| 回复字段 | 要求 |
| --- | --- |
| `story` | 必需、非空字符串，最多100000字符 |
| `turn_id` | 必需字符串，最多64字符，与当前回合一致且未被结算 |
| `base_revision` | 必需整数，与当前快照修订号一致 |
| `inventory_ops` | 必需数组，无变化为`[]` |
| `state_ops` | 状态操作数组，无变化为`[]`；兼容旧回复省略，不表示清空已有状态 |
| `effort` | `none`、`light`、`moderate`、`heavy`之一；本剧本普通自由行动必须提供 |
| `suggestions` | 可选，0～3条字符串，每条最多80字符；不写菜单编号或已经替玩家决定的结果 |
| `character_ops` | 可选，每轮最多登记1位新人物 |
| `scene_update` | 可选，确有当前场景变化时提供对象，无变化时省略，不返回`null` |
| `memory_proposals` | 可选，每轮最多3条待确认的历史记忆建议 |

回复总长度不得超过200000字符。正常回复不加代码围栏；解析器兼容单个完整的`json`围栏，但不接受普通剧情后另附隐藏指令。重复JSON键、额外顶层字段、缺少必要字段和错误类型均会被拒绝。

## 局部资料与选中数量

本地按名称、剧本别名、保守短称、行动关联和最近变更焦点筛选物品；指代不明确时参考最近两轮已采用对话。筛选不额外调用AI，也不直接执行数量操作。查询完整库存时可以扩大范围。

`inventory.scope:"relevant"`、`complete:false`表示局部资料；`statuses`也标明局部范围。**未列出不代表不存在、数量为零或状态已解除。** 信息不足时应通过剧情确认，不猜编号，不重复创建已有物品或人物。程序最终使用本地完整快照校验。

玩家一次最多关联16种自己或在场人物实际持有的物品。`selected_items`提供完整卡片、`amounts`实际库存和正整数`selected_quantity`本轮关联数量；`inventory.items`补充其他相关物品，不重复发送选中编号。选择只在当前输入页保留，不写入存档，也不代表已经使用、消耗、转交或治疗。

同一轮对已选物品的扣除和转交累计不得超过`selected_quantity`，同时仍需满足实际归属库存。增加数量不消耗选择额度。未选物品仍可能因本轮输入而进入相关资料，但不允许凭空猜测其编号。

在场人物和主角的有效状态随本轮资料发送；场外人物在被点名、相关状态或近期对话涉及它时补充。旧档场景未知时保守保留状态资料，避免隐藏伤势。初始人物摘要由剧本提供；本局新增人物按相关性发送至多4张卡，主要人物摘要最多600字符，次要最多120字符，本地完整说明不因此被截断。

## 物品操作：inventory_ops

下表列出每种操作允许的完整字段，不得另加编号、日期、文件名或脚本指令。

| `op` | 其余字段 | 结算 |
| --- | --- | --- |
| `change_quantity` | `item_id`、`owner`、`delta`、`reason` | 已有物品增减；`delta`为非零整数，不能扣成负数 |
| `create_item` | `name`、`description`、`type`、`attributes`、`quantity`、`owner`、`reason` | 创建新定义；`quantity`为正整数，编号由程序分配 |
| `transfer_item` | `item_id`、`from_owner`、`to_owner`、`quantity`、`reason` | 转交正整数数量；来源必须足够，来源与目标不同，沿用原物品编号和描述 |

除`item_id`、`delta`、`quantity`为整数外，字段均为字符串；`attributes`无内容用空字符串。归属来自当前`owners`，不限于初始的`player`、`ella`、`world`：已确认登记的动态人物也可持有物品。`world`是无主物品归属，不是人物。

新物品`name`最多80字符、`description`2000字符、`attributes`1000字符；`type`只能为消耗品、普通物品、特殊物品，`reason`最多300字符，归属编号最多64字符。当前最多512种物品，单个归属的数量范围0～1000000000。数量为0仍保留定义，已有同名物品应修改数量，不另建同名编号；协议不支持改写已有物品定义或删除定义。

`create_item`本身不得携带`id`或`item_id`。新增编号从`next_item_id`按创建顺序分配，可由本轮后续操作引用；例如起点为12，创建后可用`item_id:12`消费新物品。整轮失败不占用编号。名称去除两端空白后不区分大小写检查重复。

描述只写外观、材质、性质与用途；实时数量和归属放在数量字段，不写进会随库存变化失效的描述。属性不重复名称、类型、计数单位、数量或归属。为兼容模型偶发偏差，解析器接受最多16项的扁平`attributes`对象，将其转换成文字；键最多80字符，值只能是文字、数字或布尔值，总文字最多1000字符，嵌套结构、数组和`null`拒绝。正常输出仍使用属性字符串。

## 人物状态操作：state_ops

人物卡维护形象和认识边界；实际发生的伤势、疾病、中毒和其他持续状态记录在本局`statuses`。人物编号来自当前`characters`，包含已登记的新人物；`world`不能拥有人物状态。

```json
{"op":"create_status","character":"player","name":"左臂划伤","category":"伤势","severity":"轻微","description":"左前臂有浅表划伤，尚未处理。","effects":"用力拉弓时疼痛。","reason":"本轮穿过灌木时被枝条划伤。"}
```

```json
{"op":"update_status","status_id":1,"character":"player","name":"左臂划伤","category":"伤势","severity":"轻微","description":"伤口已清洁并包扎，尚未痊愈。","effects":"用力时仍有疼痛。","reason":"本轮实际完成包扎。"}
```

```json
{"op":"remove_status","status_id":1,"character":"player","reason":"经过恢复，本轮确认伤口已经痊愈。"}
```

- 示例展示每种操作的完整字段。新状态编号和发生时间由程序分配，不接受模型自定；更新需提供完整的新文字，沿用原`status_id`、所属人物和发生时间，由程序记录更新时间。
- 同一处伤势沿用编号，名称可自然调整；同人物同类别同名状态不能重复。指代不明时先询问，不要求玩家复述固定伤名。
- 名称最多80字符，类别和程度各40字符，描述1000字符，影响500字符，理由300字符；`effects`允许空字符串。当前最多128条有效状态，物品与状态操作合计每轮最多32项。
- 仅咨询如何治疗、否定和假设不算状态变化；实际包扎不等于痊愈。自由行动若确实使用材料，应同时提出物品消耗与伤势更新，状态更新不会隐式扣材料。
- 移除后退出有效状态表，编号不复用；历史剧情仍在对话历史中。只在`story`写受伤、治疗或恢复，不会自动新增或删除状态。状态描述和影响是资料，当前不是自动扣血、治疗计时或技能加成指令。

## 疲劳与effort

本剧本启用主角`fatigue_points`，它是0～100疲劳的唯一数值来源；程序派生相应疲劳状态。普通自由行动的`effort`按整句语境表示**已经完成**的体力活动：none／light／moderate／heavy，当前由剧本换算为0／5／10／20点。交谈、询价、治疗咨询、意图、否定与假设使用`none`；只说“我累了”或“我不累”不能直接改数值。

启用疲劳点时，`state_ops`不能新增、更新或移除主角的“疲劳”类状态，也不能新建主角“精力”类状态。旧档已有主角“精力”只能以原编号、人物及类别更新，消退后可移除，不能与疲劳或伤病类别互换。休息先恢复疲劳点，再按旧兼容规则仅处理这些既有主角精力记录，不重复恢复派生疲劳，不处理NPC或伤病。

旧主角疲劳首次接入时按轻／中／重约25／50／75点折算，未知程度保守按75点；已有数值不重复转换。原说明与影响作为本地来源保留至当前疲劳消退，恢复至低于25点后清理，不逐轮发送给AI。艾拉和其他人物不使用本剧本的数值疲劳系统，仍可维护自然状态；其他未启用疲劳点的剧本继续使用其状态与恢复规则，普通劳累统一为“疲劳”，同一人物维护一条，不使用名称白名单。

## 新人物：character_ops

需要后续互动的新具名人物可登记，普通路人不必建卡。每轮最多一项，字段严格如下：

```json
{"op":"create_character","character":"复制program_context.next_character_id","name":"新人物姓名","description":"本轮已知的身份、外观和性格。","location":"已知地点名称","reason":"本轮首次相识的依据。"}
```

编号必须等于`next_character_id`，不能自己挑选。已有同名人物沿用原编号；姓名最多80字符，说明最多1200字符，地点120字符，理由300字符。生成提示要求新人用120字符以内简述，不补全未知身世或身体数值。最多128位本局新增人物，人物与归属登记各不超过256项。

所在地必须是当前地点或已知场景。新人在当前地点时，同一回复必须在`scene_update.present_characters`列出它。人物登记先校验，随后可在本轮物品归属、状态和场景中引用；采用后进入本局`dynamic_characters`，不修改初始人物卡。新人默认为次要人物，AI不能用操作更改主要／次要层级；玩家可以在人物详情中调整本局新增人物，初始人物层级由剧本指定。

## 当前场景：scene_update

```json
{
  "location": "森林边的小屋",
  "present_characters": ["player", "ella"],
  "summary": "两人在屋内商量今天的安排。",
  "reason": "本轮仍在小屋内交谈。",
  "conditions": {"门锁":"已锁"}
}
```

四个基本字段`location`、`present_characters`、`summary`、`reason`必须齐全；可选字段只有`character_locations`与`conditions`。地点最多120字符，摘要600字符且可为空，理由300字符；在场名单为最多256个已登记人物编号，不得重复。

- `location`是当前主角视角的已确认地点，不能用AI回复改变主角所在地、移走`player`或清除实际坐标。跨地点移动只能走地图路线并按距离结算；旧档主角所在地未知时，不能由剧情猜出新位置。
- `character_locations`是人物编号到明确地点的文字对象，最多256项，未更新的人物留在原地。在场人物必须位于当前地点；从在场名单移除已知同地人物，须同时给出其明确去向。场景卡存在不代表人物已经到场。
- `conditions`是当前地点的设施名称到状态文字对象，最多16项；名称60字符、状态160字符，均非空。按键局部合并，省略保留旧状态，合并后的当前地点也最多16项。
- 地点、在场人物、人物所在地或设施状态的实际变化需采用确认；仅更新摘要不额外要求确认。省略`scene_update`保留现状。它不能修改物品、伤势或时间，也不是事件完成与自然语言事实的证明。

## 长期记忆建议：memory_proposals

```json
{"summary":"主角答应第4天上午与同伴去集市，这是尚未履行的约定。","keywords":["同伴","集市","约定"],"due_day":4}
```

每轮最多3条，仅包含`summary`、`keywords`及可选`due_day`。摘要为1～500字符，关键词最多8个、每词1～40字符。仅在游戏日期明确时提供大于0的整数`due_day`，未知时省略，不从现实日期推测；到期不代表已经完成约定。

建议先进入待确认列表，玩家在历史记忆页单独采用后才参与后续召回，不能代替本轮物品、状态或场景操作。当前最多256条已确认记忆、32条待确认建议、4条置顶；重复摘要不重复加入。无效建议整批略过，列表已满时跳过额外建议并提示，不使其他合法结算失效，也不留下半批建议。

后续每轮最多召回6条相关生效记忆，其中纯日期触发且未置顶的条目最多2条；摘要只补充历史背景，当前库存、伤势、位置和实际履约记录优先。

## 程序行动与明确物品用法

`program_action`表示程序已经掷骰并确定结果。模型只续写与该结果一致的经过，`inventory_ops`、`state_ops`必须为空，省略`scene_update`，不能额外登记新人物或重复计算疲劳；`effort`用`none`。狩猎收益和结束场景由程序处理，不接受模型更改数量、扣弹药、制造伤病或移动人物。

本剧本狩猎失败、取消、截断或结算格式无效时，按同一骰点生成本地简短记录并结算一次，不重掷，也不返还已执行的行动；普通自由输入失败则不结算。入眠、休息与地图移动使用本地结果，不请求AI。实际数值和骰表见[剧本维护说明](说明.md)。

`selected_item`是玩家明确选择程序用法后提供的计划，包含物品、持有人、模式、必要的目标伤势、消耗与骰点。`context`只关联资料；`bandage`是已明确选择的包扎计划。程序包扎必须使用主角持有的合格材料；模型不得再次改变同一材料，也不得新增、覆盖或移除同一目标伤势。程序在候选副本中统一消耗并追加处理记录，伤势保持未愈，采用前可取消。原说明过长而无法完整追加记录时，在请求前提示，不截断原档案。

## 校验、确认与保存

1. 解析并校验回合标识、修订号、字段、类型、编号、归属、数量及状态；所有核心操作在候选副本中执行。无效核心字段使整轮拒绝，不部分入账或占用编号。
2. 普通非空物品操作、状态操作、新人物登记、实际场景变更、疲劳变化或程序用法消耗进入统一预览确认。只有剧情或场景摘要更新时不额外强加确认。`reason`是模型理由，不是已证明的事件凭据；交易、战斗和来源仍需按玩法与剧情核对。
3. 玩家采用后才提交候选快照、推进本轮时间并追加已采用对话；取消不改变物品、人物状态、时间或本轮活动记忆。记忆建议仍需在管理页另外采用。查看页面不重复结算。
4. 程序负责每日食材和受控行动费用，不写入AI的重复操作。`turn_id`防止同轮重复结算，`base_revision`防止过期快照覆盖当前进度。
5. 快照随本剧本的`SAVESTR:61`写入手动或自动`.sav`；没有公共外部库存或人物状态文件。读取存档恢复当时资料，新游戏复制初始卡片。旧档缺少可选字段时按相应兼容方式处理；坏快照或未知版本报错，不静默重置覆盖。

当前快照版本为1，主要保存物品及`quantities`、人物与基础资料、有效状态、动态人物及层级、场景与设施、人物所在地、地图坐标和小数行动消耗、疲劳点与旧来源、长期记忆及待确认建议，以及后续编号、最近变更焦点和回合修订信息。有效状态包含`id/character/name/category/severity/description/effects/created_at/updated_at`；已结束状态不另设永久状态档案，原剧情保留在对话历史。

建议格式不合适时清空建议并提示，合法剧情与结算仍可采用。明确数量行动却没有任何对应物品变化时可能触发“物品核对”；它仅提示采用或取消，不按自然语言改库存，也不能保证发现所有漏记或矛盾。狩猎出现可识别的收获数量矛盾时采用原规则的简短记录。当前DeepSeek官方结构化调用使用JSON模式，其他服务不强加不兼容参数；JSON模式不能替代字段与玩法校验。

请求截断、空回复、仅思考、无效JSON和非法核心操作分别提示，不自动付费重试；错误不公开服务原文、凭据或完整模型JSON。剧情字符串里的字面`<think>`不作为外层思考块删除。字段结构通过也不等于程序已经理解所有叙事事实，玩家仍可在采用前核对。

协议实现集中于运行器`NativeAI`中的`InventoryState`、`CharacterStatus`、`DynamicCharacters`、`SceneContext`、`NarrativeMemory`、`FatiguePoints`和`ItemActions`。接入与流程分别见[开发说明](../../../../docs/开发说明.md)和[剧情输入与本地状态](../../../../docs/剧情输入与本地状态.md)。
