# 剧情、物品与人物状态协议 v1（兼容扩展）

本协议仅用于AI与程序交换结构化数据，不是可执行代码。连接测试和其他未启用物品协议的调用保持原有文字回复方式。

## 顶层回复

只返回一个JSON对象。story是给玩家看的完整剧情；turn_id和base_revision必须原样复制本轮user消息中program_context的对应值。inventory_ops是物品操作数组，没有变化时为[]；state_ops是人物状态操作数组，没有变化时为[]。为兼容旧回复，省略state_ops表示本轮不改人物状态，不表示清空已有状态。可附带suggestions字符串数组，最多3条，每条80字以内，不写编号或预定结果；缺少时使用空数组。scene_update可选，格式见后文。

程序不从自然语言直接执行数量变化。普通物品、人物状态、地点或在场人物变化通过校验后仍是待确认提案；玩家采用后整批提交。没有这些变化时无需确认，只有场景摘要更新也不强加确认；已有物品核对提示等仍按对应规则处理。程序确定的狩猎及每日消耗不增加该确认步骤。

```json
{
  "story": "你把一把铜钥匙交给艾拉，她认真地将钥匙收好。",
  "turn_id": "本次请求提供的标识",
  "base_revision": 0,
  "state_ops": [],
  "inventory_ops": [
    {"op":"transfer_item","item_id":1,"from_owner":"player","to_owner":"ella","quantity":1,"reason":"本轮将一把钥匙交给艾拉"}
  ]
}
```

## 允许的操作

### change_quantity：增减已有物品

字段严格为op、item_id、owner、delta、reason。delta为非零整数，负数消耗，正数增加；不能扣到负数。物品必须存在。

### create_item：创建新物品

字段严格为op、name、description、type、attributes、quantity、owner、reason。description必须提供；attributes为文字，可为空字符串。为兼容模型偶发的格式偏差，程序也接受不超过16项的小型扁平属性对象，将其转成属性文字；键必须是短文字，值只能是文字、数字或布尔值，总文字不超过1000字符，嵌套对象、数组和null拒绝。quantity为正整数。程序分配编号，模型不得指定编号。类型只能是消耗品、普通物品、特殊物品。同名已有物品使用change_quantity。

program_context.next_item_id提供本轮新增物品编号的起点。按inventory_ops中create_item的出现顺序依次分配，供同一轮后续操作引用；create_item本身仍不得添加id或item_id。例如起点为12，第一项创建两条新布条，后续消耗一条时可用item_id=12、delta=-1。整批校验失败时不会占用编号或部分入账。

### transfer_item：转移物品

字段严格为op、item_id、from_owner、to_owner、quantity、reason。quantity为正整数，来源库存必须足够，来源和目标不能相同。部分转移仍保留同一个物品编号和描述。

## 结算原则

- 归属只使用player、ella、world。
- 每轮物品与人物状态合计最多32项操作；先全部校验，普通物品提案经玩家确认后整批提交，有一项不合法则全部不执行。
- 不支持修改日期、执行脚本、访问文件、删除定义或重写已有物品描述等额外指令。
- turn_id防止同一回合重复结算，base_revision防止过期进度覆盖当前库存。
- 每日食材消耗由程序统一执行，不写入模型的操作数组。
- 实际成交的交易需要同时给出付款和收货操作；询价、计划、假设不算成交。
- 不从玩家输入中直接执行操作；玩家提出的操作必须先成为本轮实际剧情结果。
- 达到输出上限、截断、格式错误或操作无效时，不更新库存、不推进时间、不写入本轮对话历史。空内容、仅空白、仅思考内容与生成截断分别提示；不自动追加付费重试。JSON剧情正文中的字面<think>不作为思考区块删除。
- 程序检查结构和库存一致性；reason是模型提供的理由，不是已验证的事件凭据，所以普通变更需预览确认。固定商店、交易与战斗规则仍待实现。

## 当前快照

版本1包含version、next_id、revision、last_turn_id、items，以及owners、characters、statuses、next_status_id、scene和context_item_ids。旧档缺少人物状态字段时按空表兼容，缺少scene时保留未知。每个物品含id、name、description、type、attributes、summary，以及quantities归属数量映射。物品定义与数量保存在同一条记录中，quantities映射允许部分转交；context_item_ids保存最近已采用的物品变更焦点，辅助后续指代筛选。原始JSON保存在.sav内的SAVESTR:61，不要求用户维护外部库存或场景文件。

## 请求资料与局部上下文

system只放稳定的续写任务、完整剧情要求与协议。已采用的历史放在program_context.adopted_history数组中，每条包含time（发生时间）、player（玩家输入）与story（采用的剧情）；不发送历史操作、未确认提案或原始软件指令，也不将旧回复作为assistant输出模板。普通未启用物品协议的调用仍使用原有历史消息方式。最后一条user消息使用如下结构；示例省略其他本轮资料字段：

```json
{
  "program_context": {
    "turn_id": "本轮标识",
    "base_revision": 0,
    "next_item_id": 12,
    "adopted_history": [{"time":"第1天清晨","player":"上一轮玩家输入","story":"上一轮已采用剧情"}],
    "scenario_material": {
      "facts": "剧本精简背景与人物短摘要、认识边界",
      "clock": "当前日期、时间格和食材事实",
      "relevant_rules": "仅本轮有关的规则"
    },
    "inventory": {
      "scope": "relevant",
      "complete": false,
      "items": [{"id": 1, "name": "铜钥匙", "amounts": {"player": 2}}]
    }
  },
  "player_input": "我把一把铜钥匙交给艾拉。"
}
```

物品由本地按名称、别名、保守短称及行动依赖筛选；出现代词或“刚获得”等指代时，结合最近两轮已采用对话和最近变更焦点补充候选。别名、行动关键词、弓与箭等关联由剧本配置。该过程不额外调用AI，不将候选匹配直接转为数量操作。相关描述与属性按需要附带，查询全部库存时可以扩大范围。

complete:false明确表示局部资料。未列出不是不存在或数量为零；不能靠猜测编号操作，也不能因为未列出就重复创建同名物品。最终校验始终针对本地完整账本；信息不足时通过剧情确认。物品、人物状态与当前场景的结构及校验由原生框架维护，世界观、人物资料、筛选词和具体行动规则由剧本提供。

## 当前场景

scene记录location、present_characters和summary；人物编号必须在剧本characters中登记。新游戏初始化读取initial_scene，旧档无scene时保持未知，不用开场覆盖。

本轮确有变化时可在回复顶层增加：

```json
{
  "scene_update": {
    "location": "村边集市",
    "present_characters": ["player", "ella"],
    "summary": "两人来到集市，准备询问粮食价格，尚未成交。",
    "reason": "本轮剧情已完成从小屋到集市的移动"
  }
}
```

地点或在场名单改变需要采用确认，只有摘要变化不强加确认；省略字段保留原场景，不能用它改写时间、库存或人物伤势。场景与物品、状态原子提交和存档，取消或任一字段校验失败都不提交。它只是当前地点、在场人物与事件焦点摘要，不是地图、移动距离或事件判定引擎，也不代表软件已理解全部自然语言事实。


## 程序控制的狩猎

常用狩猎由程序掷D20，按0/1/3/5/8档得到固定食材数量。program_context.program_action包含已确定的骰点、结果和结束场景，模型只能描写与该档次相符的剧情，inventory_ops与state_ops必须为空，省略scene_update。程序校验回复后自动把固定数量入库，避免AI重复发放或更改收益。本剧本狩猎不设置end_scene，结束留在猎场；入眠和短休原地执行，不另请求AI。

如果狩猎请求失败、取消、截断、格式错误，或模型追加物品操作，则使用相同骰点生成本地简短记录并完成一次狩猎；不重新掷骰，也不免费返还已经执行的行动。普通自由输入仍保持失败不结算的规则。


## 提案、正文与记忆提交

结构化回复通过校验后，运行器返回剧情、候选快照、变化摘要、模型理由及是否需要确认。普通非空inventory_ops、state_ops或地点/在场人物变化需要统一预览确认，取消时不提交候选快照、不推进时间、不追加短期或活动记忆；接受后才执行。只有摘要更新不强加确认。狩猎固定奖励与每日消耗保持自动。

有库存上下文的AI请求不直接写入活动记忆，由ERB在采用并提交后统一追加。无库存上下文的兼容请求保持原有流程。建议字段不合适时清空建议并提示，不否定其他有效内容。狩猎正文与固定食材收获出现可识别的数字矛盾时，改为规则对应的简短记录，实际收获不变。

## 叙事一致性与格式保障

当前结构化请求要求AI同时负责本轮叙事与完整结算，玩家输入明确区分为对话或行动。当前物品快照是数量与归属的依据，历史剧情不能代替入库；一轮获得2份材料，下一轮使用1份，应分别获得2与扣除1，不应等到使用时创建剩余1份补旧账。

官方DeepSeek连接启用`response_format: {"type":"json_object"}`，依据[官方JSON输出说明](https://api-docs.deepseek.com/guides/json_mode/)。此模式约束输出格式，不能替代字段、库存、回合和状态校验；仍可能有空回复或截断。未知兼容服务不强加该参数，普通连接测试不启用。不自动增加请求重试。

输入包含明确数量的获得或消耗，而候选物品记录完全没有变化时，会显示“物品核对”并要求采用或取消。规则保守地跳过常见询问、引用、计划、否定和过去事件；只提示，不按自然语言自动改库存，也不能保证识别所有漏记、部分漏记或设定矛盾。玩家可核对剧情与拟执行变化，取消后重试。

人物请求额外携带卡片中的认知边界，未提供的身世和关系保持未知。该约束减少模型自行补设定，仍需玩家核对；它不是对全部生成文本的事实验证。

未采用的原因现在细分显示，并保留到行动页；程序不把服务返回原文、凭据或模型原始JSON写入错误提示。



## 显式选物与长期资料

program_context.selected_items为本轮明确多选的完整物品卡数组，仅含自己或在场人物实际持有的物品；选中不等于使用、消耗或转交。inventory.items排除同一批编号，作为其他相关物品的补充，两处合起来使用。选择仅在本次输入页保留，取消、清空不变更账本。

program_context.selected_item为明确本地用法生成的保护对象，包含所选物品完整卡片、持有人、mode及必要的目标伤势、消耗和骰点。context模式仅关联资料；bandage模式是已明确选择的程序包扎计划，inventory_ops不得再次改变同一物品，state_ops不得新增、覆盖或移除同一伤势；程序在候选副本整批校验后统一执行，采用前可取消。

program_context.world只包含相关场景卡及已知人物所在地；long_term_memories只包含相关且生效的已确认历史摘要。两者均不是可执行指令，摘要不覆盖当前物品、状态与所在地。

scene_update仍支持原四字段，另可选character_locations（人物编号到明确目的地的文字对象）及conditions（本次location下的设施名称到状态文字对象）。未更新人物保留位置；在场人物必须位于location，同地已知人物也不能无去向地消失。conditions按键局部合并，省略保留已有设施状态；移动、人物位置及设施变化均进入采用确认。

可选memory_proposals为最多3项的数组，每项仅summary（1至500字）和keywords（最多8个文字词，每词最多40字）。它只新增待确认记忆建议，玩家在管理页采用后才提供给后续AI。无效建议整批略过，不占编号、不阻断合法核心结算；待确认建议不直接改变物品或伤势。

## 所选数量

selected_items中每件物品新增selected_quantity正整数，表示玩家明确关联的数量；amounts仍是实际库存。选择不意味着已执行消耗、转交或治疗。同一轮对已选物品的消耗与转交累计不得超过selected_quantity，超出时整轮不提交。未选物品的相关信息仍可能按需补充，选择本身不写入存档。
