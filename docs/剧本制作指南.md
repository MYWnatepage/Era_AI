# 剧本制作指南

适用运行器：Era_AI 0.3.0。本文面向希望制作和分享新剧本的作者，按“跑通最小示例 → 填写设定 → 接入本局数据与AI → 测试 → 打包”的顺序介绍。

第一次制作先完成第一部分；它只需要两个文件，可以直接复制运行。人物、物品、地图和AI结算在后续逐步加入。当前仍需编写少量ERB，填写世界观文字不会自动生成完整游戏流程。

框架目录、字段全集和接口参考见[开发说明](开发说明.md)，结构化回复见[AI交互协议](../游戏/ERB/script/艾拉的奇幻冒险/AI交互协议.md)，玩家操作见[使用说明](../使用说明.md)。

## 准备工具与目录

准备一个能运行的0.3.0游戏副本，以及能保存UTF-8的文本编辑器。JSON保存为UTF-8，ERB建议保存为UTF-8带BOM。制作剧本本身不要求重新编译C#；修改运行器功能时才需要开发环境。

本文路径以源码仓库为例。玩家包如果直接包含`EraAI.exe`、`CSV`和`ERB`，就以该目录为游戏根目录，省略下面路径最前面的`游戏/`。

| 文件类型 | 用途 | 是否自动执行 |
| --- | --- | --- |
| `.json` | 登记身份、文字资料、人物、场景及可选规则 | 按已实现字段读取，不能任意添加字段当作功能 |
| `.ERB` | 初始化、菜单、行动、保存恢复和AI请求流程 | 引擎加载并解释执行 |
| `.md` | 给玩家和维护者看的说明 | 不自动变成游戏规则或AI提示词 |

初次测试请用独立游戏副本。复制游戏时排除个人`配置/`、`数据/`、存档、日志、`profile`、`setting.json`和`emuera.config`；需要AI时在副本里自行配置连接。测试副本和旧脚本备份放在`ERB`目录外，避免被引擎当成另一套脚本加载。

## 第一部分：先跑通林间驿站

### 创建文件夹

建立以下结构：

```text
游戏/
└─ ERB/
   └─ script/
      └─ 林间驿站/
         ├─ 剧本.json
         └─ 流程.ERB
```

这里只新增自己的文件夹，不修改`ERB`第一层、`CSV/GameBase.csv`或艾拉剧本。其他作者的包可以并存；每个包使用不同的剧本ID与函数前缀。

### 写入剧本.json

把下面完整内容保存为`林间驿站/剧本.json`：

```json
{
  "format_version": 1,
  "id": "forest_post",
  "name": "林间驿站",
  "author": "你的名字",
  "type": "日常",
  "version": "0.1",
  "entry": "FOREST_POST_START",
  "resume": "FOREST_POST_RESUME",
  "init": "FOREST_POST_INIT",
  "save_caption": "FOREST_POST_SAVE_CAPTION"
}
```

需要先理解的几个名称：

| 项目 | 本例 | 修改要求 |
| --- | --- | --- |
| 文件夹名 | `林间驿站` | 可使用中文，方便整理 |
| 显示名称 | `name`中的林间驿站 | 显示给玩家，可以修改 |
| 稳定编号 | `id: forest_post` | 1～64位英文字母、数字、下划线或短横线；发布后保持稳定 |
| 函数前缀 | `FOREST_POST_` | 所有本包函数使用独立前缀，避免与其他包重名 |
| 剧本版本 | `version: 0.1` | 作者自己的版本号，与运行器0.3.0分开 |

以本例制作自己的作品时，统一替换JSON中的`id`、读取存档和历史接口里的`forest_post`，以及全部`FOREST_POST_`函数与标签前缀。只改显示名称不会形成新的存档身份；同ID的两个包不能同时安装。发布后继续沿用自己的稳定ID。

`entry`和`resume`为必需入口。这个示例另外提供`init`和`save_caption`，分别负责新局初始化与存档标题。所有填入的函数名都必须在包内真实存在。

JSON不能有注释、重复键或结尾多余逗号。字段使用本文的准确名称；例如不能自行增加`initial_items`，也不能把`characters`改成人物对象数组。

### 写入流程.ERB

把下面完整内容保存为`林间驿站/流程.ERB`：

```erb
@FOREST_POST_INIT
DAY = 1
TIME = 0
FLAG:0 = 0
SAVESTR:1 '= "你推开林间驿站的门。柜台上放着一本留言簿，窗外的小路通向森林。"
RETURN 1

@FOREST_POST_START
$FOREST_POST_MENU
CLEARLINE LINECOUNT
CALL APPLY_DISPLAY_SETTINGS
DRAWLINE
PRINTL 林间驿站
DRAWLINE
PRINTFORML %SAVESTR:1%
PRINTFORML 已观察 {FLAG:0} 次。
DRAWLINE
PRINTL [1] 观察驿站
PRINTL [2] 保存进度
PRINTL [3] 读取进度
PRINTL [0] 返回标题
ESCAPE 0
INPUT
SELECTCASE RESULT
    CASE 0
        RETURN
    CASE 1
        FLAG:0 += 1
        SAVESTR:1 '= "你翻开留言簿，看到有人留下一句：沿小路向东，可以找到一条溪流。"
    CASE 2
        SAVEGAME
    CASE 3
        CALL LOAD_SCENARIO_SAVES, "forest_post"
ENDSELECT
GOTO FOREST_POST_MENU

@FOREST_POST_RESUME
CALL FOREST_POST_START
RETURN

@FOREST_POST_SAVE_CAPTION
RESULTS:0 '= STRFORM("林间驿站 观察{FLAG:0}次")
RETURN 1
```

这套入门骨架提供观察、保存、读取与返回，不调用AI，不包含物品、食材、疲劳或移动结算。正文提到“小路”和“溪流”只是故事文字，不会自动建立地图地点。

- `FOREST_POST_INIT`只在新游戏调用；作者自用的变量必须在这里初始化。
- `FLAG:0`保存观察次数，`SAVESTR:1`保存当前正文，均会随存档保存。
- `FOREST_POST_RESUME`继续菜单，不能再次调用初始化，否则会覆盖读回的进度。
- `SAVESTR:0`由框架保存剧本编号，作者不要改作其他用途。
- 函数和标签在引擎内统一解析，文件夹并不会自动提供独立命名空间。

### 首次运行与验收

1. 关闭测试副本，放入上述文件后重新启动。
2. 在“开始新游戏”中选择“林间驿站”。
3. 观察两次，确认次数增加到2，正文改变。
4. 保存到一个槽位，再观察一次，让次数变成3。
5. 读取刚才的存档，确认次数回到2，正文恢复。
6. 返回标题，再开始这个剧本的新游戏，确认次数重新为0。
7. 与另一个剧本并存时，确认两者都能进入、同号存档互不覆盖。

本例的原始两文件已在真实引擎的隔离副本中验证过并存、独立安装、初始化、行动、存档标题、按剧本保存、读取进入`resume`和返回。自动验证用固定槽位替代了人工选槽，未逐项点击保存界面；作者仍应手动检查自己的菜单和保存操作。

## 第二部分：填写世界观与人物

先写清下面几件事，再接入更多玩法：

- 世界是什么样的，故事发生在哪里。
- 主角是谁，其他重要人物是谁，他们彼此知道什么。
- 开场已经发生了什么，什么仍是未知或待选择。
- 玩家可做哪些行动，什么结果需要程序记录。

### 登记人物与文字资料

把第一部分的`剧本.json`替换为下面的完整扩展示例，并在下一节添加同目录的`场景卡.json`。原来的入口函数名保持不变。

```json
{
  "format_version": 1,
  "id": "forest_post",
  "name": "林间驿站",
  "author": "你的名字",
  "type": "日常冒险",
  "version": "0.1",
  "entry": "FOREST_POST_START",
  "resume": "FOREST_POST_RESUME",
  "init": "FOREST_POST_INIT",
  "save_caption": "FOREST_POST_SAVE_CAPTION",
  "owners": {"player": "旅人", "keeper": "守站人", "world": "无主"},
  "characters": {"player": "旅人", "keeper": "守站人"},
  "major_characters": ["player", "keeper"],
  "content": {
    "world": "森林边缘有一座供旅人歇脚的驿站。",
    "player_brief": "主角是一位谨慎的旅人，正在寻找旧友留下的消息。",
    "keeper_brief": "守站人说话爽快，熟悉附近道路，但不知道主角的过去。",
    "opening": "你走进驿站，守站人正整理柜台上的留言簿。"
  },
  "world_file": "场景卡.json",
  "initial_scene": {
    "location": "林间驿站",
    "present_characters": ["player", "keeper"],
    "summary": "旅人和守站人正在柜台前见面。"
  },
  "default_suggestions": ["询问留言簿", "观察驿站"]
}
```

这些登记各有职责：

- `characters`只登记“人物ID → 显示名”，不会自动形成完整人物形象。
- `major_characters`指定初始主要人物，不自动补齐性格、身世或经历。
- `owners`登记物品归属。人物需要持有物品时，人物ID和归属ID应对应；仓库和无主归属不必成为人物。
- `content`保存作者自定键名对应的文字；本例的`world`、`player_brief`等不是引擎固定关键词，必须由ERB主动读取、展示或送入本轮资料。
- `initial_scene`是开场资料，后面创建本局快照并显式初始化后才成为当前场景。

### 建立场景卡

将下面内容保存为同目录的`场景卡.json`：

```json
{
  "format_version": 1,
  "scenes": [
    {
      "id": 1,
      "name": "林间驿站",
      "description": "森林边的一间木屋，柜台上放着留言簿，窗边有供旅人歇脚的长凳。",
      "adjacent": [],
      "facilities": ["柜台", "长凳"],
      "aliases": ["驿站"],
      "rules": "可以在这里交谈、观察。"
    }
  ]
}
```

地点编号为唯一正整数。增加第二处地点时，`adjacent`填写已有地点编号，不填写自身或重复编号；名称、别名也要避免冲突。

场景卡说明地点是什么；`rules`中的自然语言不会自动实现交易、休息或开锁。实际行动仍由剧本流程和已接入规则控制。精细三维地形、建筑和溪流布局还需配置场景卡的`map_file`及地图JSON，写一句“这里有河”不会自动生成相应地形。

### 让开场文字真正显示

在`FOREST_POST_INIT`中，将原来给`SAVESTR:1`赋固定开场的那一行换成：

```erb
RESULTS:0 '= "opening"
AICONNECTION 50
IF RESULT < 0
    RETURN -1
ENDIF
SAVESTR:1 '= RESULTS:0
```

重新开始新游戏，确认展示的是JSON里的新开场。`content`中写了文字，并不意味着引擎会自行寻找它并播放；其它背景和人物条目也需要同样读取。

需要年龄、身高、体重和初始健康时，可使用开发说明中的96号接口。它只管理身体资料，不能代替性格与关系；未确定的资料保持未知，不填0占位。不要在读档入口重新设置人物健康或清掉伤势。

## 第三部分：建立本局状态和初始物品

### 建立本局快照并发放初始钥匙

在`流程.ERB`末尾追加下面的函数：

```erb
@FOREST_POST_INIT_STATE
AICONNECTION 30
IF RESULT < 0
    RETURN -1
ENDIF
SAVESTR:61 '= RESULTS:0

RESULTS:0 '= SAVESTR:61
RESULTS:1 '= "1"
RESULTS:2 '= "房间钥匙"
RESULTS:3 '= "开启驿站房门的铜钥匙。"
RESULTS:4 '= "普通物品"
RESULTS:5 '= "用途=开门"
RESULTS:6 '= "1"
RESULTS:7 '= "player"
RESULTS:8 '= "驿站房间钥匙"
AICONNECTION 31
IF RESULT < 0
    RETURN -1
ENDIF
SAVESTR:61 '= RESULTS:0

RESULTS:0 '= SAVESTR:61
AICONNECTION 57
IF RESULT < 0
    RETURN -1
ENDIF
SAVESTR:61 '= RESULTS:0
RETURN 1
```

然后在`FOREST_POST_INIT`最后的`RETURN 1`之前插入：

```erb
CALL FOREST_POST_INIT_STATE
IF RESULT < 0
    RETURN -1
ENDIF
```

重新开局时，30创建本局快照，31添加钥匙，57套用已登记的开场地点。这里的`SAVESTR:61`是本例选择的存档字段；除框架占用的`SAVESTR:0`外，作者应自己规划并记录变量用途。

初始物品的编号必须唯一，归属必须已登记；类型仅为“消耗品”“普通物品”“特殊物品”。增加物品时完整设置31所需输入，再回写成功返回的快照；失败时返回错误，不把错误文字当作快照保存。

这份扩展配方也已在并存和独立的真实引擎副本中验证：两位初始人物在场、钥匙归主角且数量为1，读回存档仍为1；没有重复初始化或发放。

这一步仅构建数据，第一部分的菜单尚未加入背包、人物页或地图入口。作者需要按[开发说明](开发说明.md#erb桥接接口)接入对应页面；例如先取当前快照再调用97可浏览场景，85和89/90分别用于物品矩阵和人物页面。别把“数据已登记”与“菜单已接入”混为一件事。

30、31、57只在新局初始化执行，`resume`保持读取后的快照。初始物品卡负责起点，游戏中新产生的物品、数量、人物状态和场景变化留在本局快照；不要反写初始JSON或ERB来保存进度。

## 第四部分：接入AI剧情与状态变化

本地骨架跑通后，再接入AI。单独填写`default_suggestions`或背景文字不会出现一个可交互的AI页面。

### 先区分新局历史与读档历史

接AI后，在`FOREST_POST_INIT`的`RETURN 1`之前增加以下代码。它只用于新游戏，不能放进`resume`：

```erb
SAVESTR:60 '= "[]"
RESULTS:0 '= SAVESTR:60
RESULTS:1 '= "forest_post"
AICONNECTION 21
IF RESULT < 0
    RETURN -1
ENDIF
```

这里选用`SAVESTR:60`保存对话快照。框架的通用新游戏入口不会自动清掉本剧本的外部对话JSON；如果省略这一步，同一剧本ID第二次开新局时可能带入上局对话。新局从空历史开始，读档则恢复当时历史，两条路径必须分开。

把下面两项加入现有`剧本.json`的同一个顶层对象，注意与相邻字段之间的逗号；不要用这个两字段片段覆盖整份登记文件：

```json
{
  "before_save": "FOREST_POST_BEFORE_SAVE",
  "after_load": "FOREST_POST_AFTER_LOAD"
}
```

再在`流程.ERB`末尾追加对应真实函数：

```erb
@FOREST_POST_BEFORE_SAVE
RESULTS:0 '= "forest_post"
AICONNECTION 20
IF RESULT < 0
    RETURN -1
ENDIF
SAVESTR:60 '= RESULTS:0
RETURN 1

@FOREST_POST_AFTER_LOAD
RESULTS:0 '= SAVESTR:60
RESULTS:1 '= "forest_post"
AICONNECTION 21
IF RESULT < 0
    RETURN -1
ENDIF
RETURN 1
```

只有“登记了钩子”和“实现了同名函数”同时具备，框架才会按时调用。首次加入AI历史功能时先用新游戏验证；早期本地骨架存档没有完整历史快照，保留旧档需要另行实现兼容处理，不能假装恢复了当时不存在的完整对话。

这组历史配方已用本地接口验证：新局清空旧历史，保存对话A后再出现对话B，读回存档只恢复A，同ID再次开新局仍为空。该验证没有向模型发送请求；作者接通实际模型后仍需检查生成、取消和错误回复。

### 一次结构化AI回合的调用顺序

1. 在测试副本的设置中配置模型连接；测试请求可能产生费用。
2. 输入页读取玩家原话，按需要关联物品。初始人物的相关性格、关系及认识边界由剧本主动放入本轮材料。
3. 用50读取`content`条目，及时存入局部变量；每次接口调用可能覆盖`RESULTS`数组，不能假定上次结果仍在。
4. 用54把精简事实、当前时间和相关规则封装为安全JSON材料，立即把返回材料保存到局部变量，再进行下一次接口调用。避免手工拼接未转义JSON，不把完整库存和所有旧对话塞入材料。
5. 以完整本局快照和玩家原话调用34准备当前回合，再调用`AISTART`，剧本编号始终为`forest_post`。
6. 等待并轮询`AIPOLL`；Esc取消走`AICANCEL`。失败或取消不把普通候选变化写入本局，不自动付费重试。
7. 成功后先保留返回的完整剧情、候选快照、变化、建议及是否需要确认。存在普通事实变化时，让玩家明确采用或取消。
8. 采用时用35校验候选快照，再回写作者选定的快照字段，按本剧本规则推进时间，并用22记录已采用对话。未采用的剧情不写入正式历史。
9. 保存和读取时使用上一节已登记的20/21钩子，捕获或恢复本局原始对话；不要读档后保留未来对话。

完整参数、结果数组和生命周期约定见[开发说明](开发说明.md#物品状态与请求)，各类JSON变化见[AI交互协议](../游戏/ERB/script/艾拉的奇幻冒险/AI交互协议.md)。需要逐字显示时接入`NARRATIVE`和`NARRATIVEPOLL`，见[显示与动画说明](显示与动画说明.md)。

普通回合由程序先校验再采用。已由程序确定骰点和收益的行动有自己的结算时机，不能套用“取消等待就撤销一切”；新增这种行动前，先理解协议中的受控行动边界。

历史记忆和当前账本分别维护：摘要可以提示过去的承诺，但不能直接证明付款、治疗或移动已经完成。初始主要人物的描述也不会因为登记了`major_characters`而自动发送，作者要主动组织相关材料。

## 第五部分：设置自己的玩法

先写清每条规则的触发条件、结果和保存位置，再决定如何实现。

| 设计内容 | 应处理的位置 |
| --- | --- |
| 世界观、已知人物形象、开场 | 作者资料与相关回合材料 |
| 初始人物、物品和场景 | 新局初始化 |
| 实际物品数量、人物持续状态、人物位置 | 本局快照 |
| 固定行动、允许地点、耗时、日结 | 剧本规则及ERB流程 |
| 剧情措辞、合理过程和建议 | AI续写，按协议提出变化 |
| 长期事件摘要和约定 | 已确认历史记忆 |

省略食材和疲劳规则，不会自动启用艾拉的“每天2份食材”或疲劳玩法。也不要直接照搬艾拉的完整菜单：86等通用可用性接口仍会读取相应参数；没配置`ticks_per_day`、`hunt_ticks`等规则时，应先使用本例自己的简单菜单。

当前框架支持已有接口和规则组合。独立战斗系统、复杂交易、障碍通行或新动画等能力可能需要额外开发，不能只增加一个JSON字段就启用。可参考[艾拉维护说明](../游戏/ERB/script/艾拉的奇幻冒险/说明.md)理解成熟示例，再选择本剧本需要的部分。

## 常见错误与排查

| 现象 | 先检查什么 |
| --- | --- |
| 剧本选择页看不到新剧本 | 是否放在正确的`ERB/script`下，登记文件是否准确命名为`剧本.json`，修改后是否重启 |
| 提示重复编号 | 是否复制模板后忘记改`id`；编号忽略大小写比较，重复时相关包会被停用 |
| 启动时报函数重名 | 是否保留别的包的函数前缀，或把备份ERB也放在加载目录 |
| 登记失败或JSON错误 | 字段拼写、重复键、末尾逗号、字符串引号、文件编码，以及非空钩子是否真实存在 |
| JSON写了开场或人物形象却没显示 | ERB是否主动读取相应`content`并展示或组装材料 |
| 新物品没出现在本局 | 是否只写了说明；是否真正调用初始化桥、检查返回结果并回写快照 |
| 读档后物品重发、状态重置 | `resume`是否错误地再次执行30/31/57或新游戏初始化 |
| 改了初始设定，旧档没有变化 | 旧档保存本局资料；验证新的初始设定应重新开局，迁移要另行实现 |
| AI剧情变化没有进账 | 是否准备结构化回合，是否返回正确提案，是否通过校验并被采用 |
| 另一剧本同号存档被覆盖 | 是否通过框架选择当前剧本并使用稳定ID，是否绕开通用存档路径直接写文件 |

排查时先在副本复现，保留错误说明；分享截图或日志前遮挡密钥和私人对话。不能用清空玩家数据来掩盖迁移问题。

## 发布前检查与打包

- 新局能进入，初始物品只发放一次，未配置的玩法没有被意外启用。
- 菜单编号、返回、输入取消和长文字显示正常。
- 手动保存、读取、返回后继续及新游戏重置均符合预期。
- 与艾拉等其他包并存时，没有重复函数、编号冲突或同号存档覆盖。
- 若启用了AI：采用、取消、错误格式、网络失败、建议及记忆的行为均测试过；测试范围和已知限制写明。
- 所有文件使用包内可用路径，素材来源和许可清楚，记录所需运行器版本。

分享包的外层保留你的剧本文件夹，里面包含`剧本.json`、ERB、所用场景/地图资料、必要素材和一份给玩家看的安装与内容说明。告诉玩家解压到游戏的`ERB/script/`下，重启后选择剧本。

不夹带整套游戏、个人密钥、`配置/`、`数据/`、存档、对话、用量或测试日志。发布后保留剧本ID；新版本改变初始资料或字段时，应说明是否需要新局及旧档如何处理。制作过程不需要新建Git分支或标签；在维护者指定的工作方式下保存即可。

这个指南中的林间驿站只作为文档内的入门示例，没有安装进正式游戏的剧本列表。需要制作时由作者复制上述内容建立自己的包。
